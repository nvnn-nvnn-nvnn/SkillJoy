# 188 — Image and video background templates

Date: 2026-08-24
Migrations: none

Ten shipped background images, a sixth preset category, and the rules that make
an asset safe for a *shared* template. Presets now: **30 across 6 categories.**

---

## 1 · The actual problem: an asset needs an owner, or it needs none

`bg_image` and `bg_video` were in `THEME_PORTABLE_EXCLUDE`, so a theme export
stripped them. That exclusion was right, and the reason matters:

> An **uploaded** background lives in one creator's storage bucket. A preset
> pointing at it would hotlink their file and bill **their** bandwidth for
> everyone else's page views.

So the original validator banned `bg: 'image'` outright — right reason, wrong
scope. The rule isn't *"no images"*, it's **"no asset that belongs to
somebody"**.

An asset shipped in `public/templates/` has no owner and no bill. That is the
one safe exception, and it is now the only one:

```js
export const TEMPLATE_ASSET_PREFIX = '/templates/';
const isShippedAsset = (v) => typeof v === 'string' && v.startsWith(TEMPLATE_ASSET_PREFIX);
```

Applied on both sides of the portable-theme boundary — export keeps it, import
accepts it. **The prefix check is also the security boundary:** it is a
same-origin path, so a hand-edited theme file cannot smuggle an external URL
through the import whitelist.

> **Transferable:** when a blanket ban blocks something you legitimately need,
> re-read *why* the ban exists. Usually the reason is narrower than the rule,
> and the fix is to encode the actual reason — not to add an exception.

## 2 · SVG, not JPG

Ten backgrounds — five mesh gradients (`aurora`, `dusk`, `mint`, `peach`, `ink`)
and five patterns (`grid`, `dots`, `waves`, `topo`, `stars`).

**All ten together: 37 KB.** One photographic JPG would be bigger than the set.

Generated by `scripts/gen-backgrounds.cjs`:

```js
const blob = (cx, cy, r, color, op = 0.85) =>
  `<circle cx="${cx}" cy="${cy}" r="${r}" fill="${color}" opacity="${op}" filter="url(#blur)"/>`;
```

Three overlapping blurred circles *is* a mesh gradient — the same look a design
tool exports at 400 KB, at about 600 bytes. Why SVG:

- loads on every page view, so size is not a detail
- resolution-independent: sharp on a 5K monitor and on a phone
- editable in a text editor — recolour one without a design tool
- no binary blobs in git history

One detail worth stealing, in `stars.svg`:

```js
const h = (i * 2654435761) >>> 0;   // seeded hash, not Math.random()
```

A **deterministic** scatter, so regenerating produces a byte-identical file and
git shows no diff when nothing changed. `Math.random()` would make every run a
spurious 8 KB commit.

## 3 · Video: the poster is not optional

No video ships yet (no ffmpeg here to encode one), but the path is built and
tested. Three states where a background video renders **nothing**:

1. before it loads
2. on a connection that never finishes loading it
3. under `prefers-reduced-motion`, where `.sf-bgvideo` is now hidden outright

All three previously fell through to a flat colour. Now `bg_image` doubles as
the poster and is painted *underneath* the video:

```jsx
<video src={theme.bg_video} poster={theme.bg_image || undefined} preload="metadata" … />
```
```js
// bgStyle now covers video too, so the still sits under the moving picture
((theme.bg === 'image' || theme.bg === 'video') && theme.bg_image) ? { backgroundImage: … } : …
```

The checker **requires** `bg_image` on any video preset, and caps videos at
**3 MB** — every visitor downloads it before the page settles, on whatever
connection they have.

> **Transferable:** any element that takes time to appear needs a defined
> appearance for the time before it does. "It'll pop in" is a decision made by
> not making one.

## 4 · Two places the swatch was lying

Scenic presets **are** their background — so a picker that painted a flat colour
showed all ten as the same grey tile. Both the editor's `swatchStyle` and the
onboarding tile now branch on `image`/`video` first and render the real asset.

That is the third time this session a preview omitted what the control changes
(notes 181 §4, 184 §4). Adding a background *type* means finding every surface
that renders a background *summary* — there were two.

## 5 · Mutation-tested, again

The video rules exist for cases I could not produce a file for, which makes
testing them more important, not less. Each was verified by adding a
deliberately-wrong preset, confirming the specific error fires, and reverting:

| Case | Result |
|---|---|
| `bg:'video'` with no `bg_video` | ✓ caught |
| video with no poster | ✓ caught |
| asset path not on disk | ✓ caught |
| external `https://` URL | ✓ blocked |
| `card_opacity: 100` over an image | ✓ warned |

**One test bug found while doing it:** the first run reported the
`card_opacity` case as MISS. The guard was fine — warnings go to `stderr`, and
on a passing run `execSync` returns only `stdout`, so my harness never saw them.
Worth remembering: a test that captures one stream will silently under-report
exactly the diagnostics that don't fail the build.

## Addendum — the build badge (note 186, exercise 1)

A dev-only pill in the bottom-left showing **DEV · <time the server started>**.
Hovering says "You are NOT looking at production." Click collapses it to a dot,
remembered in `localStorage`.

This is the instrument note 186 said should have existed. "Is this build even
running?" is the cheapest of the three "it doesn't show up" causes
(LANDMINES §15) and was historically checked last — three rounds of size
adjustments were made against the deployed site before anyone asked which URL
was open. Now it is a glance.

`vite.config.js` stamps the time via `define`:

```js
const BUILD_STAMP = new Date().toISOString();
export default defineConfig({
  define: { __BUILD_STAMP__: JSON.stringify(BUILD_STAMP) },
```

### It leaked into production on the first attempt

The component started with:

```jsx
export default function BuildBadge() {
  const [open, setOpen] = useState(…);
  if (!import.meta.env.DEV) return null;   // ← too late
```

Grepping `dist/` found the whole component still in the production bundle. The
guard ran at *runtime*, after a hook, so Rollup could not prove the body was
dead — and the module was imported unconditionally by `main.jsx` anyway.

Moving the gate to the **mount site** fixed it:

```jsx
{import.meta.env.DEV && <BuildBadge />}
```

`import.meta.env.DEV` is a compile-time constant, so the branch folds to
`false && …`, the JSX is dropped, and the module tree-shakes away. Verified by
grepping the built bundle, not assumed.

> **Transferable:** "dev only" enforced by an early `return null` still **ships**
> the code. To actually exclude it, the condition has to be resolvable at build
> time and placed where the reference itself disappears. And check the artifact
> — a dev-only feature you never grepped for is a dev-only feature you hope is
> dev-only.

One eslint follow-on: `__BUILD_STAMP__` is injected by `define`, so it exists at
runtime but in no source file. Declared in `eslint.config.js` as
`globals: { ...globals.browser, __BUILD_STAMP__: 'readonly' }` rather than
silenced with a disable comment — the former documents where it comes from.
